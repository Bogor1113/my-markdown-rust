Product Review · Desktop App

MyMdEdit 产品诊断与优化路线图
从「功能齐全」到「产品可信」

以 Windows 桌面级应用的产品标准，对 MyMdEdit v1.0.74 做一次全景诊断：定位、缺口、优先级与落地路线。

版本 v1.0.74 栈 Tauri 2 + Rust + React 19 内核 Milkdown / ProseMirror + CodeMirror 6 日期 2026-09-16 方式 代码实证盘点

00结论先行

一句话判断：功能广度已经超过 Typora，但产品成熟度还差一个身位。它现在是「一堆好功能的集合」，还不是「一个可信赖的产品」——差距不在编辑器内核，而在安装之后的完整生命周期。

  1. 最致命的是数据安全感缺口。无本地历史/版本、无崩溃恢复、无独立备份目录。2 秒防抖自动保存直接写盘，等于「改错即覆盖原文」，且崩溃发生在保存窗口内就会丢内容。这是唯一会让用户「失去信任」的类别。
  2. Windows 原生化只做了一半。自绘标题栏、托盘、拖放、文件关联、单实例都有；但窗口尺寸/位置/最大化状态不记忆、无自动更新、无跳转列表、无全局快捷键、无「跟随系统」深浅色——这些正是用户判断「像不像专业软件」的地方。
  3. 规模一旦上来就会撞墙。全局搜索是每次全量递归扫描（无索引、不读 .gitignore、不流式返回、不可取消）；编辑器对大文档无虚拟化。单目录几百篇课件没问题，上千篇就会明显变慢。
  4. 设置面板过于单薄（仅 4 项）。本质问题是「可控感」不足：默认打开模式、行号/折行、Tab 宽度、图片粘贴行为、备份间隔、启动行为、面板布局都不给用户选。
  5. 护城河应选「中文写作 + 教学/课件 + 本地零依赖」。导出 6 格式、片段库、中文排版优化、Markdown 校验、公众号复制、EPUB 这套组合是真实差异点，应围绕「讲稿生产流水线」继续加深，而不是去追 Obsidian 的双链图谱。

先做什么：四象限

01产品定位与竞品坐标

定位决定取舍。MyMdEdit 不应与 Obsidian 争「第二大脑」，而应占住「中文写作 + 课件/讲稿生产 + 本地零依赖」这个位置。

03问题清单：按优先级排

P0 影响信任与数据，P1 是体验硬伤，P2 是可感知的打磨，P3 是增强与探索。

P0 · 立刻要解决（影响信任）

P0
没有本地历史与版本恢复 误删、误改、粘贴覆盖，全都无法回退
现状
自动保存是 2 秒防抖后直接覆盖写盘。回收站只保护「删除文件」这一种操作，不保护「改坏内容」。
影响
老师备课改错一段、学生误粘贴覆盖课件，撤销栈关掉窗口就没了。这是会让用户不敢用的第一原因。
建议
在应用数据目录建 history/<文件hash>/时间戳.md，每次保存前留一份快照，滚动保留最近 7 天 / 50 版；提供「文件历史」面板做对比与回滚。成本不高，但价值极高。
P0
没有崩溃恢复与错误日志 渲染进程一崩，未保存内容直接蒸发，且无从定位
现状
前端无 ErrorBoundary、无 window.onerror 捕获；Rust 侧无日志文件；崩溃后无「恢复上次编辑」入口。
影响
2 秒自动保存窗口内崩溃 = 丢内容。更麻烦的是崩溃后完全无迹可查——上一轮反馈的「源码模式空白 / 网络图片不加载 / WebView2 停止工作」到现在都没能闭环，根因就是缺日志。
建议
三件事：① 编辑缓冲持久化到 localStorage（每 500ms，写 dirty buffer），启动时检测并提示恢复；② 加 ErrorBoundary + 全局错误捕获，写本地日志文件；③ 加「导出诊断日志」按钮，方便反馈问题。
P0
HTML 块直接 innerHTML 渲染，未做清洗 课件里粘贴的 HTML 可执行脚本
现状
plugins/html.ts 用 dom.innerHTML = value 直接渲染块级/行内 HTML，未接 DOMPurify。
影响
课件若来自外部（学生作业、网上下载的 md），恶意脚本可在应用上下文执行。桌面应用通常不需要提权，但可读取本地文件、窃取内容。
建议
接入 DOMPurify 白名单清洗（保留 img/table/svg 等常用标签与 style），半天工作量。顺带把 release 构建的 devtools feature 去掉，并收紧 CSP 中仅开发环境需要的 localhost:1420 放行。
P0
关闭行为不透明，用户以为退出了实际还在后台 关闭 = 隐藏到托盘，但没有任何告知
现状
点关闭按钮直接 hide()，无提示、无托盘气泡；托盘图标被 Windows 折叠时用户找不到应用。
影响
常见误解「我关了怎么还在运行」，或反复双击图标无反应（被单实例挡住）。
建议
首次关闭到托盘时弹一次气泡/提示「已最小化到托盘，点击托盘图标可恢复」，并提供「关闭时最小化到托盘」开关（默认开）；同时在设置里给出「彻底退出」的明确路径。

P1 · 体验硬伤（决定「像不像专业软件」）

P1
窗口尺寸、位置、最大化状态不记忆 每次启动都是固定 1280×820
现状
未引入 window-state 能力，窗口几何完全由配置写死。
影响
双屏用户每次都要重新摆放窗口；最大化状态丢失。属于 Windows 桌面的基本素养，缺失感极强、修复成本极低。
建议
引入 tauri-plugin-window-state，一行配置即可记忆尺寸/位置/最大化。约 1 小时。
P1
没有自动更新机制 装了 v1.0.x 就永远是 v1.0.x
现状
已有 NSIS 打包与单实例，但无 updater 通道，也无「检查更新」入口与更新日志页。
影响
修复与改进无法触达用户；老师群体通常不会主动来问「最新版在哪」。对自研/内部分发产品，这是迭代闭环的断点。
建议
接 tauri-plugin-updater（签名 + 静态 JSON 清单即可，无需服务器），做「启动静默检查 + 设置页手动检查」；同时加「关于」页展示版本与更新日志。
P1
规模化性能：搜索与渲染都会撞墙 小目录没问题，大知识库会明显变慢
现状
全局搜索每次调用都全量递归遍历 + 逐行匹配，结果一次性返回；无索引、不读 .gitignore（仅硬编码跳过 node_modules/target 等）、无流式增量、无取消。编辑器对大文档无虚拟化（10MB 以上仅提示转源码模式）。
影响
课件目录上千篇后，搜索会卡住数秒且不能中止；十万行级别的单文件编辑会掉帧。
建议
搜索侧：用并行遍历 + ignore 规则（尊重 .gitignore/.mdignore）+ 结果流式推送（事件分批）+ 取消令牌。渲染侧：设置「超过 N 行自动进源码模式」的可配阈值 + 编辑器分块渲染/视口裁剪。另加启动与首次渲染耗时埋点，先量化再优化。
P1
设置面板过于单薄，用户没有「可控感」 只有 4 个选项：字号、自动保存、拼写、标题编号
现状
绝大多数行为写死在代码里，用户无法调整。
影响
不同用户的工作习惯差异巨大（有人要行号、有人要折行、有人要默认源码模式），没有开关就会产生「这软件不合我用」的判断。
建议
按分组扩到 5 类：编辑器（默认打开模式、行号、折行、Tab 宽度、字号、字体）、文件（自动保存间隔、备份保留份数、图片保存位置与命名、大文件阈值）、视图（主题与跟随系统、侧边栏/大纲默认显隐、状态栏项目）、导出（默认格式、PDF 页边距与页码、是否内联图片）、系统（关闭行为、开机自启、语言、检查更新）。
P1
面板不可控：侧边栏/大纲无法手动开关 布局由代码决定，用户不能自定义工作区
现状
大纲面板仅在「当前文档有标题」时自动出现，没有显隐开关；侧边栏也没有折叠按钮；没有「视图」菜单。
影响
想专注写作时必须拖拽宽度或进全屏（会连工具栏一起隐藏），缺少「只留编辑器」的干净布局。
建议
加视图菜单与快捷键：切换侧边栏（Ctrl+B 已占用则用 Ctrl+Shift+B）、切换大纲、切换状态栏、禅模式（隐藏所有面板仅留正文）。
P1
标签页能力偏弱 不能拖拽排序，也没有「重新打开已关闭」
现状
已有右键「关闭当前/左边/右边/非当前」，但无拖拽重排、无最近关闭恢复、无「复制路径 / 在资源管理器中显示 / 打开所在文件夹」。
建议
补 4 项：标签拖拽排序、Ctrl+Shift+T 重新打开、右键复制路径/在资源管理器中显示、双击标签区新建文件。

P2 · 精细化打磨（细节即品质）

#问题影响建议
1 公众号/知乎复制后配图会裂 粘贴到平台后图片全是本地路径，等于半截功能 复制时把图片内联为 dataURL（小图）或提示「先上传图床」；或恢复一个可控的图片上传（剪贴板直传）
2 命令面板覆盖不全 导出 EPUB、新建文件、打开文件夹、每日笔记、切换面板都不在命令里 把所有可执行动作统一注册进命令表，面板与工具栏共用同一份定义（避免两处维护漂移）
3 快捷键无冲突检测与配置迁移 改冲突了不知道；换机器要重设 录制时即时检测冲突并提示；设置面板加「导出/导入快捷键配置」
4 无「最近关闭」与跨目录最近文件 误关标签只能重新找文件 内存 + localStorage 维护最近关闭栈（10 个），支持 Ctrl+Shift+T
5 状态栏信息不足 缺光标行列、选区字数、编码、换行符（LF/CRLF）、缩放百分比 状态栏右侧补这些状态项，允许在设置里选择显示哪些
6 无「关于 / 更新日志 / 反馈」入口 用户遇到问题无处反馈，也不知道新版本改了什么 设置里加「关于」页：版本、构建时间、更新日志、一键复制诊断信息
7 Toast 与提示体系单一 长任务（导出、搜索、批量替换）无进度、不可取消 引入进度条式 Toast 与可取消操作，耗时任务统一走它
8 空状态与首次体验无引导 首次打开只见「打开文件夹或文件」，不知道能做什么 首次启动向导：选择目录 → 介绍 3 个核心能力（源码模式、导出、片段库）→ 提供示例文档
9 图片插入流程不统一 粘贴/拖入图片的落盘位置、命名规则、是否压缩不明确 统一为「同目录 .assets 子目录 + 相对路径引用」，设置里可改命名模板并可选压缩
10 错误文案偏技术化 如「自动保存失败：xxx」直接抛原始错误 统一错误映射为人话 + 建议动作（如「文件被占用，请关闭其他程序后重试」），附「复制详情」
11 无「跟随系统」深浅色 多套主题很漂亮，但要手动切 加 system 主题选项，监听系统主题变化实时切换
12 Ctrl+滚轮缩放无重置与可视化 缩放到 32px 后想回默认只能再滚回去 加 Ctrl+0 重置为 100%、状态栏显示缩放百分比、设置里给「恢复默认字号」

P3 · 增强与探索（做之前先想清楚为什么）

Windows 原生化（性价比高）

  • 任务栏跳转列表：右键任务栏图标直达最近文件 / 新建文件
  • 资源管理器右键「新建 Markdown 文档」：写 shell new 菜单，老师建课件更顺手
  • 全局快捷键快速记录：如 Ctrl+Alt+N 任意位置唤起小窗速记并落盘到收件箱
  • 开机自启（可选）+ 托盘常驻，配合速记形成习惯
  • 缩略图工具栏（任务栏预览上的按钮）、系统通知（保存失败/导出完成）

教学场景闭环（差异化护城河）

  • 演示模式：大纲驱动的全屏翻页讲稿，一行一页、代码高亮渐进显示，讲课直接用它
  • 模板与变量：课件模板 + {{日期}} {{学期}} {{章节号}} 占位符自动填充
  • 练习/答案分离导出：同一份文档一键导出「学生版（挖空）」与「教师版（含答案）」
  • 作业收集批改**：批量打开学生 md → 统一校验/统计 → 汇总报告
  • 课件体检：把已有的链接/图片校验升级为「结构体检」（标题层级跳级、代码块未闭合、图片缺失、术语一致性）

知识组织（选择性做）

  • 建议只做轻量标签 + [[文件名]] 跳转，不做完整双链图谱——那是 Obsidian 的主场，投入产出比低
  • 跨目录「最近文件」与「收藏夹」比双链更实用
  • 若做索引，可同时支撑搜索加速与「相关文档」推荐

同步与备份（BYO 而非自建）

  • 不做自建云：接 WebDAV / S3 兼容 / 坚果云等，用户自带账号
  • 更轻的方案：一键导出/导入配置与片段库、把备份目录放在用户指定的同步盘内
  • 本地历史快照本身就是最好的「穷人版版本控制」，优先于云同步

04Windows 桌面专项：专业度体检

用户对「是不是专业软件」的判断，80% 来自这些操作系统层面的细节，而不是编辑器本身。

项目现状缺口 / 建议优先级

05性能、可靠性与安全专项

性能：先量化，再优化

目前没有任何性能埋点，所有判断都靠感觉。建议先加三组指标，再针对性优化。

  • 启动：进程启动 → 首屏可交互耗时（目标 <1.5s）
  • 打开：不同体积文档（10KB / 1MB / 10MB）的打开耗时
  • 输入：5 万字文档连续输入的帧率与按键延迟
  • 搜索：100 / 1000 / 10000 篇文档下的 P95 耗时
  • 内存：长会话（2 小时）内存增长曲线，重点看 Mermaid / KaTeX 缓存是否无界

可靠性：把「不会丢」做成承诺

  • 编辑缓冲持久化：未保存内容定期写入本地，启动检测并恢复
  • 保存失败可视化：已有提示，建议升级为「失败横幅 + 重试 + 另存为」
  • 写入冲突处理：文件被外部修改时给出「覆盖 / 保留我的 / 对比」三选一（现依赖 watcher 刷新，可能悄悄覆盖）
  • 只读与锁定文件：明确提示，不静默失败
  • 权限异常：目标目录不可写时的降级路径（保存到用户文档目录并告知）

安全：桌面应用也有攻击面

  • HTML 清洗（DOMPurify）——当前 P0 缺口
  • release 关闭 devtools feature，避免用户侧可开控制台
  • 收紧 CSP：生产包移除 ws://localhost:1420 等开发放行
  • 外链打开：统一走系统浏览器，禁止应用内导航到外部页面
  • 剪贴板富文本：已有转义，保持
  • 注册表写入：文件关联需可撤销、可查询，并在设置里显式暴露

可观测性：没有日志就没有修复

本项目的典型困局是「用户说有问题，但复现不了」。上一轮的三个现象（源码模式空白、网络图片不加载、WebView2 停止工作）至今未闭环，根源就是缺少运行时可观测性。

  • 本地日志文件（按天滚动，保留 7 天），记录：启动、打开/保存、导出、错误堆栈
  • 崩溃标记：异常退出后下次启动提示「上次未正常退出，是否查看日志 / 恢复未保存内容」
  • 「导出诊断包」按钮，一键打包日志 + 环境信息，方便反馈

08附录：未闭环问题与验证方法

上一轮反馈的三个现象尚未完成根因闭环，建议以「先补可观测性、再复现」的方式收尾，而不是继续猜。

现象当前状态建议的定位方法
源码模式不显示源码 在 Chromium（dev 与打包预览）下均无法复现，疑似 WebView2 环境特有 在 WebView2 真实环境中打开控制台观察 CodeMirror 挂载与异常；同时记录源码模式切换时的 DOM 结构与错误日志。若确认为环境问题，加入降级兜底（挂载失败时回退为纯文本 textarea + 提示）
课件中 HTML 网络图片不加载 代码路径正确（http/https 原样透传、已设 no-referrer），CSP 的 img-src 亦放行。仅在打包环境出现 在打包环境用「图片加载失败」占位类（mditor-html-img-error）统计失败率；用开发者工具查看具体请求的 Network 状态与被拦截原因（CSP / 防盗链 / 混合内容）。重点验证第三方图床对空 Referer 的策略
WebView2 停止工作 高度怀疑与调试端口参数、多实例争用同一用户数据目录有关，需排除环境因素 确认是否由本地调试注入的浏览器参数造成；清理残留 WebView2 进程后以正常方式启动验证；长期方案是为应用固定独立用户数据目录并在崩溃时记录事件日志
方法论提醒：这三个问题的共同点是「只在打包环境出现」。这恰好印证了本报告的核心判断——缺少运行时可观测性，是这个项目当前最大的工程债。补上日志与错误捕获之后，同类问题都会从「猜」变成「查」。
